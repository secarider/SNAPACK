# SNAPACK Display Layout (Version 1.0)

## Firmware Architecture

Tier 1 establishes the production firmware architecture with a deliberately
simple diagnostic user interface. Tier 1 code is not considered throwaway.

Sensor acquisition, measurement processing, safety logic, fault-state handling,
nonvolatile storage, and hardware control shall remain separate from
SquareLine-generated UI files.

SquareLine/LVGL files are the presentation layer and shall remain replaceable
without requiring the underlying application logic to be rewritten.

LVGL access shall remain within the UI execution context. Sensor, safety,
storage, and hardware-control tasks shall communicate through a defined
application-state interface, queue, or equivalent thread-safe mechanism.

The existing Elecrow display driver, touch support, rotary navigation, splash
behavior, and useful ring/arc animations shall be preserved wherever practical.

## Pack Resistance Monitoring —

SNAPACK shall estimate overall pack-path resistance during suitable high-current load events, including engine cranking.

The calculation shall use the measured change in final output voltage and measured change in output current:

**Estimated Resistance = Voltage Change ÷ Current Change**

The measurement represents the complete active output path, including:

* Battery cells
* Cell and pack interconnections
* Bus bars
* Active contactors
* Internal high-current wiring
* Output cables and connections included within the measurement points

### Required Behavior

* Continuously monitor output voltage and current.
* Detect suitable current-load events automatically.
* Capture stable pre-load voltage and current values.
* Capture loaded voltage and current values during the event.
* Pre-load and loaded measurements used for a single resistance calculation
  shall be taken from the same stable operating mode and active contactor
  configuration.
* Measurements spanning a 12V / 16V mode transition or contactor-state change
  shall be rejected for resistance calculation.
* Calculate estimated pack-path resistance in milliohms.
* Reject results from events that do not provide a sufficient and reasonably
  stable current change, contain invalid sensor data, occur during a contactor
  or operating-mode transition, or otherwise cannot produce a trustworthy
  resistance estimate.
* Record the peak current and minimum loaded voltage associated with each accepted measurement.
* Store accepted resistance results in nonvolatile memory.
* Retain resistance history for comparison over time.
* Display the latest valid resistance estimate.
* Identify increasing resistance as a possible indication of battery aging, loose connections, contactor degradation, cable degradation, or another high-current-path problem.

### Measurement Record

Each accepted resistance measurement should include:

* Estimated resistance in milliohms
* Pre-load voltage
* Loaded voltage
* Pre-load current
* Loaded or peak current
* Temperature at the time of measurement
* 12V or 16V operating mode
* Event number or timestamp, when available
* Valid or rejected measurement status

### Accuracy Expectation

This is a practical DC load-event resistance estimate intended for pack-health trending and high-current-path diagnostics. It is not required to duplicate laboratory AC impedance testing.

The implementation shall use the existing final-output voltage and OTC current measurements. No additional resistance-measurement hardware is required unless testing proves that the installed sensors cannot provide a repeatable result.


## Design Philosophy

* Favor simple, readable information over maximum data density.
* Show only information requiring attention.
* Use summary displays whenever all systems are healthy.
* Reveal detailed information only when requested or when an abnormal condition exists.
* Build from the existing Elecrow demo rather than redesigning the interface.

## Temperature Behavior

## Low Temperature Charge Protection

Purpose:

Protect LiFePO4 cells from charging at temperatures below the configured
minimum safe charging temperature.

Required Behavior:

• Continuously monitor all five temperature sensors.

• The lowest measured sensor shall determine pack charging eligibility.

• A missing, failed, disconnected, or otherwise invalid temperature sensor
  shall not be treated as a safe temperature for charging.

• If temperature-sensor health is insufficient to determine that all required
  battery temperatures are safely above the charging limit, charging
  authorization shall be withheld until valid temperature monitoring is restored.

• Temperature-sensor failure shall not, by itself, prohibit discharge unless
  another defined safety condition requires it.

• If every measured temperature is above the configured limit,
  normal operation continues.

• If one or more sensors are below the configured limit:

    • Pack discharge remains fully permitted.

    • Pack charging remains permitted until reverse current is detected.

• If reverse current is detected while any temperature is below the
  configured charging limit:

    • Remove positive authorization.
    • De-energize both contactor banks.
    • Display:

        COLD CHARGE BLOCKED

    • Record the event in the event log.

• The system shall continue monitoring temperature and current.

• Operation shall automatically resume only after:

    • all temperatures exceed the release threshold, and
    • reverse current is no longer present.

This cold-charge fault uses automatic recovery as defined above and is not
normally a latched fault requiring user acknowledgment.

Configuration:

• Charge Inhibit Temperature
• Charge Release Temperature (hysteresis)
• Reverse Current Threshold
• Enable / Disable Cold Charge Protection

## Temperature Agreement / Abnormal Temperature Behavior

Read all five temperature sensors continuously.

If all five temperatures agree within the configured allowable spread:

* Display the average temperature.
* Indicate ALL NORMAL.

If one or more temperature readings do not agree with the normal group:

* Identify the affected location by assigned sensor name.
* Display the differing temperature prominently.
* Continue displaying all five sensor readings.
* Display the average of the agreeing normal-temperature group separately.

A temperature reading that differs significantly from the other sensors shall
not automatically be classified as a failed sensor.

A differing reading may represent a genuine localized hot or cold condition
and shall remain visible to the operator.

Sensor-health faults shall be determined separately using available evidence
such as missing communication, invalid readings, disconnected probes,
impossible values, repeated communication errors, or other clearly unreliable
sensor behavior.

A sensor confirmed or reasonably determined to be faulty may be excluded from
the normal-group average, but its fault condition and assigned name shall
remain visible to the operator.

The implementation may use median-based deviation or another robust method
to identify temperature disagreement and establish the normal-temperature
group, provided that a genuine localized temperature condition is not
silently discarded as a sensor fault.

## Screen 3 — TEMPS

Detailed temperature-monitoring screen.

Display all five temperature sensors simultaneously by their assigned names:

* POS CABLE
* NEG CABLE
* EV200 BUS
* LEFT LEV100
* RIGHT LEV100

Each sensor shall display its individual current temperature.

Temperature units default to degrees Fahrenheit and may be changed through
the configured Temperature Units setting.

When all five sensors agree within the configured allowable spread:

* Indicate ALL NORMAL.
* Display the normal-group average temperature.
* Keep all five individual sensor readings visible.

When one or more temperatures differ significantly from the normal group:

* Identify each affected location by assigned sensor name.
* Display each differing temperature prominently.
* Visually distinguish the differing temperature from the normal-temperature group.
* Continue displaying all five sensor readings.
* Display the average of the agreeing normal-temperature group separately.

A differing temperature shall not automatically be labeled as a failed sensor.

If a sensor-health fault is independently detected, identify the affected
sensor by assigned name and clearly indicate SENSOR FAULT or equivalent
rather than presenting the condition as a genuine temperature difference.

Sensor names shall remain associated with their assigned DS18B20 ROM addresses
as defined by the temperature-sensor commissioning configuration.

Temperature warnings may use the existing ring / arc animation behavior where
appropriate, provided readability and monitoring performance are not compromised.

Serial diagnostics should include, where applicable:

* ADS1115 detection and I2C address
* Raw ADS1115 channel readings
* Converted voltage and current values
* DS18B20 detection and unique ROM addresses
* Assigned DS18B20 sensor names
* Individual temperature readings
* Final output positive and negative measurements
* Current operating mode
* Active warning or fault states
* Contactor authorization / commanded state
* Relevant safety-state transitions

The diagnostic display shall present the primary measurements needed for
hardware verification without requiring the finished Tier 2 presentation.

Diagnostic functionality belongs to the permanent firmware architecture
and should remain available for future troubleshooting even after the
production user interface is completed.

### Safety / Fault Behavior

Safety thresholds shall use appropriate hysteresis and debounce where needed
to prevent rapid state changes caused by noise or values near a threshold.

Temperature disagreement, genuine overtemperature, and temperature-sensor
health faults are separate conditions and shall not automatically be treated
as equivalent faults.

A temperature that differs significantly from the other locations shall remain
visible and shall be evaluated against the applicable safety thresholds.
A genuine localized high-temperature condition shall not be discarded merely
because the other temperature sensors remain normal.

A temperature-sensor health fault shall be identified separately using available
evidence such as missing communication, invalid or impossible readings,
disconnected probes, repeated communication errors, or other clearly unreliable
sensor behavior.

Loss of sufficient valid temperature information shall fail safe for functions
that require temperature authorization. In particular, charging shall not be
authorized when the firmware cannot establish that all required monitored
locations are within the permitted charging-temperature range.

Temperature-sensor failure shall not, by itself, prohibit discharge unless
another defined safety condition requires it.

Each safety fault shall define its recovery behavior as either:

* Automatic recovery after safe conditions are restored.
* Latched until reset or user acknowledgment.

The Low Temperature Charge Protection behavior defined earlier is an
automatic-recovery condition and shall follow its separately defined inhibit,
release, reverse-current, and recovery rules.

Serious fault conditions shall remove positive authorization and command the
appropriate contactor state through the processor-controlled safety output.

Firmware safety logic supplements the hardware fail-safe design and shall not
assume that continued normal firmware execution is the sole means of placing
the system into a safe state.

Active warnings and faults shall remain identifiable to the operator by type
and affected location whenever that information is available.

### Lifetime Records

Peak values, accepted resistance measurements, settings, and event records
shall be stored in nonvolatile memory as appropriate.

Nonvolatile writes shall be event-driven, thresholded, debounced, or otherwise
limited so continuously changing measurements do not cause unnecessary flash wear.

* Reset Peak Current
* Reset Highest Temperature
* Reset Lifetime Statistics
* Clear Event Log (future)

## Animated Ring and Semantic Color Behavior

Existing Elecrow ring and arc animations should be retained wherever practical.

The ESP32-S3 hardware is expected to support simple LVGL ring rotation, pulsing, 
color changes, and screen transitions without affecting sensor monitoring.

Animation rules:

* Animation must remain secondary to readability.
* Important numeric values must remain clearly visible at all times.
* Normal conditions use calm motion and subdued colors.
* Warning conditions use stronger contrast and pulsing 
with another ring within the ring.
* Critical conditions use red and a more urgent animation/pulsing.
with posibly another ring within the other 2 for 3 rings withing each other ring
* Crank-current colors follow the configured Green / Yellow / Red thresholds.
* Temperature warnings may highlight the affected named location with a pulsing ring.
* Sensor-health faults shall be visually distinguishable from genuine temperature warnings.
* If animation ever interferes with reliable sampling or display updates, 
the animation is reduced or disabled before any monitoring function is compromised.

possibilities:


Cranking Screen — Dynamic Temperature Status
During an active cranking event, reserve a temperature-status area adjacent to the primary cranking-current display. 
Under normal conditions, this area may display the current average pack temperature or remain visually subdued. 
If the existing temperature-monitoring logic detects an abnormal sensor condition or 
rapid temperature rise during the cranking event, the normal temperature indication is 
immediately replaced by a prominent identification of the affected sensor and its current temperature. 
The indication remains visible during the cranking event so the operator does not need to 
leave the cranking screen to observe a developing thermal condition.

KNOWN ANIMATION / BACKGROUND SERVICE HISTORY
--------------------------------------------
Step68 demonstrated an important serial-backpressure problem.

With recurring temperature Serial.print diagnostics active:

- Terminal reader running -> UI/ring smooth.
- Terminal reader stopped for approximately 7-8 minutes ->
  approximately 1-second UI freeze every 5 seconds.
- Restarting terminal reader -> hitch disappeared almost immediately.

CONCLUSION / PERMANENT SNAPACK DESIGN RULE:

Recurring or nonessential Serial.print diagnostics must NEVER be
allowed to block the ESP32 UI/control loop when no host serial reader
is consuming output.

This is important not merely for animation but for future:

- current monitoring
- temperature monitoring
- thermal rate-of-rise detection
- contactor authorization
- protection logic

Step70 recurring temperature service is serial-silent.

THERMAL PROTECTION
------------------
STATUS: PLANNED - NOT IMPLEMENTED

Future thermal protection is intended to include TWO independent
mechanisms:

1. Absolute overtemperature protection.

2. Abnormal temperature rate-of-rise protection.

A rapidly heating connection may therefore cause protection action
before reaching the absolute high-temperature threshold.

Future thermal fault consequence:

Withdraw authoritative power/authorization from contactors.

Exact thresholds are deliberately NOT established yet.

They must be determined from installed-system testing.


NORMAL VS HIGH-CURRENT TEMPERATURE MONITORING
---------------------------------------------
STATUS: ARCHITECTURE AGREED - NOT YET IMPLEMENTED

Normal operation:

Use relatively relaxed temperature polling to minimize DS2484/1-Wire
workload and preserve UI smoothness.

High-current event:

OTC current measurement will eventually trigger a fast thermal-watch
mode.

During high-current thermal-watch mode:

Priority order should approximately be:

1. Current acquisition
2. Temperature acquisition / rate-of-rise
3. Protection / contactor authority
4. Essential Current-screen information
5. Touch/UI responsiveness
6. Decorative ring animation

Decorative ring animation is SACRIFICIAL during a genuine high-current
event.

Perfect animation smoothness is NOT required while maximum thermal
surveillance is active.

After high current ends:

Fast temperature monitoring should continue for a suitable cooldown /
heat-soak period before returning to normal temperature cadence.

Exact:
- current trigger
- temperature cadence
- absolute temperature threshold
- rate-of-rise threshold
- cooldown duration

remain UNDEFINED until real testing provides useful data.


NOT CURRENTLY IMPLEMENTED
-------------------------
The following must NOT be mistaken for operating Step70 features:

- Temperature-triggered contactor shutdown
- Temperature rate-of-rise shutdown
- High-current fast-temperature mode
- Post-current-event thermal soak mode
- Final temperature thresholds
- Final rate-of-rise thresholds
- ADS ALERT-based authorization logic
- Temperature-based charging authorization
- Authoritative thermal contactor control
- Final OTC clamp polarity
